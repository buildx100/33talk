# 33talk

[English](https://github.com/buildx100/33talk) · [简体中文](https://github.com/buildx100/33talk/tree/main/docs/zh-CN) · **日本語**

▶ 試す: **[33talk.buildx100.cc](https://33talk.buildx100.cc/)**

**テレタイプ Model 33 が二台、並べて置かれ、一つのキーボードで動きます。**
片方は ELIZA（1966年）に、もう片方はローカルの言語モデル（2026年）につながっています。
どちらがどちらかは毎回ランダムで、**答えを見る前に予想を確定しなければなりません。**

![同じ一行に答える二台の Model 33。一方は 1966 年、もう一方は 2026 年](../screenshot.png)

二台には同じ言葉が打ち込まれました。片方の答えは、もう片方より六十年古い。
**どちらでしょう？**

機械は製品ではありません。ブラインドテストが製品です。機械は舞台です ——
そして、端末がなぜ今のような振る舞いをするのかを説明する教材として、
これまでに作られた中で最良のものでもあります。

`\r` と `\n` がなぜ別々の文字なのか、`Ctrl+C` がなぜ中断なのか、
端末がなぜビープを鳴らすのか、`stty erase` は何のためにあるのか ——
考えたことがあるなら、その答えはすべてこの一台の機械が残した化石です。
そしてそのすべてを、耳で聞くことができます。

---

## 動かす

言語モデルを含めて、コマンド一つ：

```sh
docker compose up --build
```

そして <http://localhost:16001> を開きます。モデルはイメージの中にあるので、
起動時に何もダウンロードしません。

`huggingface.co` に届かない場所では：

```sh
docker compose build --build-arg HF_HOST=https://hf-mirror.com
```

ES モジュールは `file://` では読み込めないため、
**`web/index.html` をダブルクリックしても動きません。**

## 開発

開発用オーバーレイを付けて一度起動します：

```sh
docker compose -f compose.yml -f compose.dev.yml up
```

ディスク上の `web/` をイメージの静的ディレクトリに重ねます。
**ファイルを編集してブラウザを再読み込みする — ループはこれだけです。**
再ビルドも再起動も不要で、言語モデルのコンテナには一切触れません。

このオーバーレイを `docker-compose.override.yml` と**名付けていないのは意図的**です。
そのファイル名は自動的に読み込まれるため、コミットすると本番サーバーが
自分のホスト側のファイルを黙って配信するようになってしまいます。

| | |
|---|---|
| 開発 | `docker compose -f compose.yml -f compose.dev.yml up` |
| フロントエンドだけ、コンテナなし | `npm run serve` |
| フロントエンドのイメージだけ再ビルド | `docker compose build web`（数秒） |
| 本番 | `docker compose up --build -d` |
| モデルの変更 | `MODEL_FILE` を編集し `docker compose build llm` |
| テスト | `npm test` |

**コードを変えてもモデルは再ダウンロードされません。**
モデルは別のイメージ（`Dockerfile.llm`）にあり、そちらを再ビルドしても、
`MODEL_REPO`・`MODEL_FILE`・`HF_HOST` が変わらない限り Docker のレイヤキャッシュに当たります。

**コードを名前付きボリュームでマウントしてはいけません。**
イメージが既に中身を持つパスに名前付きボリュームを重ねると、
最初の作成時に一度だけ種が蒔かれ、その後は二度と更新されません ——
再ビルドして再起動しても古いコードが配信され続け、その理由を示すものは何もありません。
バインドマウントにはこの問題はありません。

## 何が本物で、何がそうでないか

この機械の制約は一つ残らず構造材です。「使いやすくするため」に一つ取り除けば、
意味そのものが失われます。

| 本物 | |
|---|---|
| 1行 72 文字 | terminfo `cols#72` |
| 毎秒 10 文字、110 ボー | Model 33 の仕様 |
| 1インチ 6 行、紙幅 8.44 インチのロール紙 | Model 33 の仕様 |
| 大文字のみ、64 文字 ASCII | 活字ドラムに小文字は存在しない |
| **バックスペースキーがない** | キャリッジは前に進むか、復帰するかのどちらか |
| `RUB OUT` はバックスペースではない | DEL であり、紙テープの穴を全部打ち抜くためのもの |
| `LINE FEED` と `RETURN` は別のキー | 二つの機械動作 —— CR と LF が二つの文字である理由であり、Windows が CRLF を残した理由 |
| **`@` は SHIFT+P**、独立したキーではない | 1971年、Ray Tomlinson はこのキーボードからそれを選んだ |
| 72 桁目で折り返さない | その場に重ね打ちする。折り返しは**ホスト**の仕事 |
| 行末が近づくとベルが鳴る | 打鍵者への警告 —— ASCII 0x07 でも鳴る |
| キャリッジリターンには実時間がかかる | 当時のホストが CR の後に NUL を詰めた理由 |

`terminfo(5)` が実例として使っているエントリは、まさにこの機械のものです：

```
33|tty33|tty|model 33 teletype,
    bel=^G, cols#72, cr=^M, cud1=^J, hc, ind=^J, os,
```

`hc` = ハードコピー、`os` = 重ね打ち。どちらも実装されています。

| 意図的に本物でないもの | 理由 |
|---|---|
| カンニング窓 | リモートエコーという概念を映像で並べて見せるため。画面上にそう明記してあります |
| 返答ごとの `READY` | タイムシェアリング BASIC のプロンプトであり、CTSS 上の ELIZA が打つものではありません。残しているのは**両方のホストが完全に同じ書式で出力しなければならない**ためです |
| 30 / 120 CPS ボタン | せっかちな人への慈悲 |

いくつかの細部は**未確認**であり、断定せずソースにそう注記してあります：
制御コードのキートップ刻印のいくつか、`HERE IS` / `RUB OUT` / `REPT` / `BREAK` がどの段に属するか、
そしてキーボードの段のずれ量です。

## 試してみる価値のあること

| これを打つと | こうなります |
|---|---|
| `PASSWORD` ⏎ | 両方のホストがエコーを止めます。打ち続けても、どちらの紙にも何も出ません。**今日あなたが端末でパスワードを打っても表示されない、その起源です** |
| `HELLO###P` ⏎ | バックスペースはありません。`#` は一文字消し、`@` は行全体を消しますが、**その記号自身も紙に打たれます**。紙はあなたの打ち間違いを正直にすべて残します |
| `HELP` ⏎ | 機械が自分自身を、紙の上で説明します |
| バックスペースキー | 画面が一瞬ひるみ、何も起きません |
| `PRINT` | 二本の紙が一枚ずつ、実寸で —— 紙幅 8.44 インチ、1インチ 10 文字、1インチ 6 行、上下は切り取り跡 |

ヘッドホンなら、**A は左チャンネル、B は右チャンネル**です。
音はすべて Web Audio によるリアルタイム合成で、サンプルもファイルもありません。
二台のモーターは 60 Hz と 60.4 Hz に調律してあり、互いにうなりを生みます ——
同じ台の上に置かれた二台の実機のように。

## ブラインドテストの健全性

機械がどちらのホストかを漏らした瞬間に、すべてが崩れます。
そして応答時間は、最も分かりやすい経路にすぎません。

- **同期ゲート。** 両方のホストを `Promise.all` で解決し、**それから**キューに入れます。
  だから二台は同じフレームで打ち始めます。ELIZA は 0 ミリ秒で答え、
  言語モデルは 1〜3 秒かかります。これがなければ応答時間だけで即座に分かります。（`hosts.js`）
- **共有メトロノーム。** 一つのタイマーが二台を進めます。
  速度が違うことも、ずれていくこともあり得ません。（`clock.js`）
- **一つの共有ポストプロセッサ。** 大文字化、64 文字集合へのフィルタ、72 桁での折り返し、
  先頭の空行一つ、末尾の `READY` 一つ。**どちらのホストも自分の出力を整形しません。**
  返答の**形**に関するものはすべて、内容とは無関係な手がかりになります。（`format.js`）
- **1ラウンドに1回だけ。** 予想すると `REVEAL` は自分を無効化し、
  `RESHUFFLE` だけがそれを再び有効にします。
- **紙を切っても再抽選しない。** 新しい紙、同じ割り当て。
  紙を切ることが賭け直しになってはいけません。

このフィルタは**コード**でなければならず、システムプロンプトでは駄目です。
小さなモデルは何を言われようと小文字・Markdown・絵文字・曲がった引用符・ダッシュを吐き、
そしてこの機械はそれらを物理的に印字できません。

### 機械が印字できるものと、ホストが印字してよいもの

これは別の話なので、`format.js` の中でも別の関数です：

| | |
|---|---|
| `downgrade()` | **ハードウェア。** 大文字化、曲がった引用符とダッシュの畳み込み、0x20–0x5F へのフィルタ。活字ドラムが持っているもの |
| `houseStyle()` | **規約。** Markdown、句読点の語彙。**ホスト**が印字してよいもの |

この区別は構造的です。活字ドラムには `?` も `*` も**実際にあり**、
キーボードからも**実際に打てます** —— エコーは `houseStyle` を通りません。
**制限されるのは二台のコンピュータだけです。**

**句読点の語彙。** 1966年のスクリプトの再構成テンプレート 199 本すべてを数えたところ、
ELIZA の句読点の語彙は全部で四文字でした：

```
'  x34      ,  x13      -  x5      .  x1
```

二重引用符はありません。**疑問符もありません — スクリプト全体を通して一つも。**
モデルはそのすべてに手を伸ばすので、ELIZA には使えない記号は
片方の紙にだけ現れる文字になります。ホストの出力はこの語彙に畳み込まれます：
`"` → `'`（ELIZA も引用します。ただし 1966 年のやり方で —— `WHY DO YOU SAY 'AM'`）、
`;:` → `,`、`?!` → `.`、それ以外は削除。

**文末に句読点を置かない。** 199 本のうち 197 本は英数字で終わり、
残る 2 本はアポストロフィで終わります。`.?!` で終わるものは**一つもありません**。
モデルはほぼすべての文を `?` で終えます。
これは**一文字で勝てる手がかり**です —— 一語も読まずに、紙の最後の文字を見るだけで済みます。

**20 語の予算。** 実際の会話で計測した ELIZA の最長の返答より一語だけ多い値です。
モデルの中央値は 18 語、ELIZA は 8 語でした。
切り詰めるときは最後のきれいな切れ目まで予算を戻します ——
まず文末、次に節の切れ目 —— なので切り詰められた返答が文の途中で終わることはありません。

### 決定的な手がかりはコードで塞ぎ、統計的なものは塞がない

- **決定的** —— ある文字が常に片方にだけ現れ、もう片方には決して現れない。**塞ぐ。**
  文末の `?`、二重引用符、Markdown の `*`。
- **統計的** —— 分布が重なっている。生成側で形を整え、
  切るのはきれいな境界でのみ。**文の途中で切ることは、それが消す手がかりより大きな手がかりです。**

統計的な差が一つ、**意図的に開いたまま**にしてあります。20 往復の計測で、
返答の書き出しの多様性は **ELIZA 95%、モデル 23%**。
ELIZA は 199 本の手書きテンプレートをポインタで巡回します。
0.6B のモデルにあるのはシステムプロンプト一つとサンプリング分布だけです。
**これは調整では消せません。** そしてこの手がかりは**逆を向いています** ——
繰り返しが多く冗長なほうが 2026 年のホストであり、これは遊ぶ人の予想と正反対です。
テストを易しくするのではなく、難しくしています。

### 言語モデルのシステムプロンプトは役割と長さだけを決め、それ以外は何も決めない

ELIZA も DOCTOR も 1966 年も**意図的に一言も触れず**、古風に振る舞えとも言わず、
真似すべき例文も一つも与えていません。ELIZA を演じろと指示すれば、
これは物真似のテストになってしまいます。問うているのは、
**双方が同じ仕事を同じ制約の下でしたとき、六十年の差が読み取れるか**です。

## デプロイ

### 必要なもの

Docker が入った、3コア・4GB メモリのマシン。GPU も API キーも、
どこかのアカウントも要りません。モデルは CPU で動き、
毎秒 10 文字という速度では**紙のほうがプロセッサよりはるかに厳しいボトルネック**です。

### 手順

```sh
git clone <このリポジトリ>
cd 33talk
docker compose up --build -d
```

`http://<あなたのサーバー>:16001` を開きます。**デプロイはこれで全部です。**

最初のビルドでモデルをダウンロードします —— 429 MB、数分。
起動時には何もダウンロードせず、以降のビルドでも、モデルを変えない限り何もしません。

**中国本土など、`huggingface.co` に届かない場所では**ミラー経由でビルドします：

```sh
docker compose build --build-arg HF_HOST=https://hf-mirror.com
docker compose up -d
```

### 設定

**既定では設定は不要です。** 以下はすべて任意 ——
どれかが必要なときだけ `.env.example` を `.env` にコピーしてください。

| | | |
|---|---|---|
| `PORT` | `16001` | 公開ポート。16001 が使われている場合に変更 |
| `MODEL_REPO` | `ggml-org/Qwen3-0.6B-GGUF` | HuggingFace のリポジトリ |
| `MODEL_FILE` | `Qwen3-0.6B-Q4_0.gguf` | その中のファイル |
| `HF_HOST` | `https://huggingface.co` | 金盾の内側では `https://hf-mirror.com` |

モデルの変更は再起動ではなく**再ビルド**です：
`docker compose build llm && docker compose up -d`。

### 日々の操作

| | |
|---|---|
| ログ | `docker compose logs -f` |
| 停止 | `docker compose down` |
| `git pull` のあと更新 | `docker compose up --build -d` |
| フロントエンドだけ再ビルド | `docker compose build web` —— 数秒。モデルの層はキャッシュされます |

### トラブルシューティング

**ポートが使用中。** `echo "PORT=16005" > .env` のあと `docker compose up -d`。

**モデルのダウンロード中に止まる、または接続がリセットされる。**
再開します：ダウンロードは `curl -C -` をリトライループに入れており、
完了後にサーバーが申告したサイズと突き合わせて検証します。
10 回失敗するようなら上のミラーを使ってください。

**`llama-server` が起動直後に `cannot open shared object file` で終了する。**
誰かがコンテナの作業ディレクトリを変えています。**`/app` のままでなければなりません** ——
ローダーはそこを基準に `.so` を探すため、
エラーは「ライブラリが無い」と言いますが、真の原因とは似ても似つきません。

**Linux で `host.docker.internal` が解決できない。**
Compose の中ではなくホスト上で自前の推論サーバーを動かし、
そちらを指す場合にだけ関係します。`compose.yml` には既に
これを直す `extra_hosts` が入っています。
無いと、何の手がかりもない接続失敗になります。

### どう組み合わさっているか

```
ブラウザ --> nginx :16001 --+-- /       --> web/（静的ファイル）
                            +-- /v1/... --> llama-server :16002
```

コンテナ二つ。**同一オリジン**なので、ブラウザはクロスオリジン要求を一度も出さず、
CORS はこの絵に登場しません。**バックエンドのコードはありません** ——
nginx は設定であって、プログラムではありません。
**`llama-server` はホストにポートを公開していません**。入口は `/v1` プロキシだけです。

| イメージ | サイズ | |
|---|---|---|
| `33talk-web` | 48 MB | nginx + `web/` |
| `33talk-llm` | 555 MB | llama-server（39 MB）+ モデル（429 MB）、`ubuntu:24.04` の上 |

**モデルはイメージに焼き込んであります。** これは一般的な助言とは逆ですが、
モデルが小さいからこそ成り立ちます。言語モデル側が欠けていればブラインドテストは無価値なので、
「起動してから数分ダウンロードする」デプロイのほうが悪い取引です。

上流の `llama.cpp:server` イメージは 845 MB で、うちバイナリは 39 MB、
残りはビルド環境です。マルチステージビルドでその 39 MB を素の `ubuntu:24.04` に載せると、
イメージは 1.27 GB から 555 MB になります。
**`ubuntu:24.04` でなければなりません** —— `debian:12-slim` はサイズこそ同じですが
glibc が二世代古く、読み込み時に `GLIBC_2.38 not found` で失敗します。

`llama-server` 自身も静的ディレクトリを配信できます（`--path`。バイナリで確認済み。
`--cors-origins` の既定は `*`）。したがって単一プロセスのデプロイも可能です。
二サービスに分けたままなのは、推論コンテナを差し替え可能にしておくためです。

## これは何ではないか

- **Model 33 のエミュレータではありません。** [`Random832/ttyemu`](https://github.com/Random832/ttyemu)、
  `hughpyle/ttyemu`、`progs-n-things/asr33emu`、PDP-8/E シミュレータが既に、
  紙テープやシリアルのバックエンド付きで、もっと上手くやっています。
  **それらとの機能の同等性は目標ではありません。**
- **端末ではありません。** シェルも PTY も SSH もありません。
- **レトロな皮を被せたチャット UI ではありません。**

「テレタイプで AI を動かす」自体は新しくありません ——
`m15-ai/Paper-Tape-LLM` がやっていますし、hughpyle は本物の ASR-33 で言語モデルを動かしました。
**新しいのは 1966 年対 2026 年のブラインドテストです。**
